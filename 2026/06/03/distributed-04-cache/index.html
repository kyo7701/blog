分布式缓存：架构、问题与解决方案

2026-06-03 分布式 Redis, 一致性, 分布式, 缓存 0 Comments Word Count: 4.9k(words) Read Count: 16(minutes)

前言

缓存是提升系统性能的重要手段，但是当单机缓存无法满足需求时，我们就需要引入分布式缓存。分布式缓存虽然解决了容量和性能问题，但也带来了一系列新的挑战。今天就来聊聊分布式缓存的架构设计、常见问题以及解决方案

为什么需要分布式缓存

单机缓存的局限性

  1. 容量有限：单机内存有限，无法存储大量数据
  2. 性能瓶颈：单机处理能力有限，无法应对高并发
  3. 单点故障：单机宕机，缓存服务不可用
  4. 扩展性差：无法通过增加机器来提升性能

容量有限的具体表现：

假设一台服务器有64GB内存，扣除操作系统、应用程序占用的内存，真正可用于缓存的可能只有30-40GB。如果需要缓存100GB数据，单机就无法满足了

性能瓶颈的具体表现：

Redis单线程模型下，QPS可以达到10万+。但如果业务需要100万QPS，单机就无法满足了

单点故障的具体表现：

如果缓存服务器宕机，所有请求都会打到数据库，可能导致数据库崩溃

分布式缓存的优势

  1. 容量扩展：通过增加节点来扩展存储容量
  2. 性能提升：通过多节点并行处理来提升性能
  3. 高可用：通过集群和主从复制来保证可用性
  4. 负载均衡：将请求分散到多个节点

容量扩展的原理：

假设有3个节点，每个节点存储33GB数据，总共可以存储100GB数据

性能提升的原理：

假设有3个节点，每个节点处理33万QPS，总共可以处理100万QPS

分布式缓存的架构

客户端路由

一致性哈希

  • 将缓存节点映射到哈希环上
  • 数据根据哈希值映射到对应的节点
  • 节点增减时，只有少量数据需要迁移

一致性哈希的工作原理：

  1. 将整个哈希值空间组织成一个虚拟的环（0 ~ 2^32-1）
  2. 将缓存节点映射到环上
  3. 将数据映射到环上
  4. 数据由顺时针方向遇到的第一个节点负责

为什么使用一致性哈希？

传统的取模哈希（hash % n）有一个问题：当节点数量变化时，几乎所有数据都需要重新分布。一致性哈希解决了这个问题，节点增减时，只有少量数据需要迁移

哈希取模

  • 数据根据哈希值对节点数取模
  • 实现简单
  • 节点增减时，大量数据需要迁移

哈希取模的问题：

假设有3个节点，使用 hash(key) % 3 分布数据：

  • key1 -> hash(key1) % 3 = 0 -> 节点0
  • key2 -> hash(key2) % 3 = 1 -> 节点1
  • key3 -> hash(key3) % 3 = 2 -> 节点2

如果增加一个节点，变成4个节点：

  • key1 -> hash(key1) % 4 = ? -> 可能是节点0、1、2、3
  • key2 -> hash(key2) % 4 = ? -> 可能是节点0、1、2、3
  • key3 -> hash(key3) % 4 = ? -> 可能是节点0、1、2、3

几乎所有数据都需要重新分布！

代理层

  • 在客户端和缓存节点之间增加代理层
  • 代理负责路由和负载均衡
  • 代表：Twemproxy、Codis

代理层的工作原理：

  1. 客户端发送请求到代理
  2. 代理根据路由规则，将请求转发到对应的缓存节点
  3. 缓存节点返回结果给代理
  4. 代理返回结果给客户端

代理层的优点：

  • 客户端无需关心路由逻辑
  • 可以实现负载均衡
  • 可以实现读写分离

代理层的缺点：

  • 增加了一层网络通信
  • 代理可能成为性能瓶颈
  • 代理可能成为单点故障

集群模式

  • 缓存节点之间相互通信
  • 数据自动分片
  • 代表：Redis Cluster

集群模式的工作原理：

  1. 数据通过哈希槽分布到多个节点
  2. 每个节点负责一部分哈希槽
  3. 节点之间通过Gossip协议通信
  4. 客户端可以连接任意节点

集群模式的优点：

  • 无需代理，性能更好
  • 自动分片，扩展性好
  • 高可用，支持主从复制

集群模式的缺点：

  • 实现复杂
  • 客户端需要支持集群协议
  • 某些操作受限（如跨槽操作）

缓存的常见问题

缓存穿透

什么是缓存穿透

查询一个一定不存在的数据，由于缓存未命中，每次都要查数据库，失去了缓存的意义

缓存穿透的场景：

  • 恶意攻击：故意查询不存在的数据
  • 业务bug：查询逻辑有误
  • 数据清理：数据被删除但缓存未清理

缓存穿透的影响：

  • 所有请求都打到数据库
  • 数据库压力增大
  • 可能导致数据库崩溃

解决方案

1. 缓存空值

将空结果也缓存起来

工作原理：

  1. 查询缓存，未命中
  2. 查询数据库，未找到数据
  3. 将空结果缓存起来（设置较短的过期时间）
  4. 后续查询直接返回空结果

优点：

  • 实现简单
  • 效果明显

缺点：

  • 浪费内存
  • 数据不一致（数据库新增数据后，缓存仍是空值）

2. 布隆过滤器

使用布隆过滤器判断数据是否存在

工作原理：

  1. 将所有可能的数据哈希到位数组中
  2. 查询时，先检查布隆过滤器
  3. 如果布隆过滤器说不存在，一定不存在
  4. 如果布隆过滤器说存在，可能存在（有误判率）

优点：

  • 性能高
  • 内存占用小

缺点：

  • 有误判率
  • 不支持删除
  • 实现复杂

3. 接口校验

在接口层进行参数校验

工作原理：

  1. 校验参数格式
  2. 校验参数范围
  3. 过滤无效请求

优点：

  • 从源头解决问题
  • 减少无效请求

缺点：

  • 需要修改业务代码
  • 无法解决所有场景

缓存击穿

什么是缓存击穿

某个热点key过期，大量请求同时打到数据库

缓存击穿的场景：

  • 热点新闻过期
  • 热门商品过期
  • 秒杀活动开始

缓存击穿的影响：

  • 大量请求同时打到数据库
  • 数据库压力瞬间增大
  • 可能导致数据库崩溃

解决方案

1. 互斥锁

使用分布式锁，只允许一个请求重建缓存

工作原理：

  1. 缓存未命中
  2. 尝试获取分布式锁
  3. 如果获取成功，查询数据库，重建缓存，释放锁
  4. 如果获取失败，等待一段时间后重试

优点：

  • 只有一个请求打到数据库
  • 其他请求等待缓存重建

缺点：

  • 实现复杂
  • 有锁等待开销

2. 永不过期

热点数据不设置过期时间

工作原理：

  1. 缓存不设置过期时间
  2. 通过后台任务定期更新缓存
  3. 业务代码只读取缓存

优点：

  • 避免缓存击穿
  • 性能稳定

缺点：

  • 数据可能不一致
  • 需要后台任务支持

3. 提前续期

在过期前异步更新缓存

工作原理：

  1. 缓存即将过期时，触发异步更新
  2. 异步任务查询数据库，更新缓存
  3. 业务代码读取缓存

优点：

  • 避免缓存击穿
  • 数据相对新鲜

缺点：

  • 实现复杂
  • 需要定时任务支持

缓存雪崩

什么是缓存雪崩

大量缓存同时过期，请求全部打到数据库

缓存雪崩的场景：

  • 系统启动时，大量缓存同时加载
  • 缓存过期时间设置相同
  • 缓存服务重启

缓存雪崩的影响：

  • 大量请求同时打到数据库
  • 数据库压力瞬间增大
  • 可能导致数据库崩溃

解决方案

1. 随机过期时间

在过期时间上增加随机值

工作原理：

  1. 设置基础过期时间
  2. 增加随机偏移量
  3. 不同key的过期时间不同

优点：

  • 避免同时过期
  • 实现简单

缺点：

  • 随机值需要合理设置
  • 不能完全避免雪崩

2. 多级缓存

使用本地缓存+分布式缓存

工作原理：

  1. L1缓存：本地缓存（Caffeine、Guava Cache）
  2. L2缓存：分布式缓存（Redis）
  3. 查询时先查L1，未命中再查L2

优点：

  • 减少分布式缓存压力
  • 性能更好

缺点：

  • 数据一致性问题
  • 实现复杂

3. 限流降级

在缓存失效时进行限流

工作原理：

  1. 监控缓存命中率
  2. 当命中率下降时，触发限流
  3. 限流后，部分请求直接返回默认值

优点：

  • 保护数据库
  • 保证系统可用

缺点：

  • 用户体验下降
  • 需要限流组件支持

缓存一致性

什么是缓存一致性

缓存中的数据与数据库中的数据不一致

缓存一致性的场景：

  • 先更新数据库，再删除缓存：缓存可能是旧值
  • 先删除缓存，再更新数据库：可能出现脏数据

解决方案

Cache Aside Pattern

  • 读：先读缓存，缓存没有则读数据库，然后更新缓存
  • 写：先更新数据库，再删除缓存

工作原理：

读操作：

  1. 读取缓存
  2. 如果缓存命中，返回
  3. 如果缓存未命中，读取数据库
  4. 将数据库数据写入缓存
  5. 返回数据

写操作：

  1. 更新数据库
  2. 删除缓存

为什么删除缓存而不是更新缓存？

  • 避免并发写导致的数据不一致
  • 减少缓存写入次数
  • 下次读取时会自动加载新数据

Read/Write Through

  • 读写都通过缓存层
  • 缓存层负责与数据库同步

工作原理：

读操作：

  1. 读取缓存
  2. 如果缓存未命中，缓存层从数据库加载
  3. 返回数据

写操作：

  1. 写入缓存
  2. 缓存层同步写入数据库

优点：

  • 业务代码简单
  • 缓存层封装了数据库操作

缺点：

  • 缓存层实现复杂
  • 缓存层可能成为瓶颈

Write Behind

  • 写操作只更新缓存
  • 异步批量更新数据库

工作原理：

写操作：

  1. 写入缓存
  2. 异步将写操作放入队列
  3. 后台任务批量更新数据库

优点：

  • 写性能高
  • 减少数据库压力

缺点：

  • 数据可能丢失
  • 实现复杂

延迟双删

  1. 先删除缓存
  2. 更新数据库
  3. 延迟一段时间后再次删除缓存

工作原理：

  1. 删除缓存
  2. 更新数据库
  3. 等待一段时间（如500ms）
  4. 再次删除缓存

为什么要延迟？

等待其他读操作完成，避免读操作将旧数据写入缓存

为什么是双删？

第一次删除：删除当前缓存
第二次删除：删除可能被其他读操作写入的旧数据

监听binlog

  • 监听数据库的binlog
  • 根据binlog更新缓存

工作原理：

  1. 数据库写入数据
  2. 数据库生成binlog
  3. 监听程序读取binlog
  4. 根据binlog更新缓存

优点：

  • 实时性好
  • 业务代码无需修改

缺点：

  • 实现复杂
  • 依赖数据库binlog

缓存的淘汰策略

常见策略

  1. LRU（Least Recently Used）：淘汰最近最少使用的数据
  2. LFU（Least Frequently Used）：淘汰使用频率最低的数据
  3. FIFO（First In First Out）：先进先出
  4. TTL（Time To Live）：根据过期时间淘汰

LRU的工作原理：

  1. 维护一个访问链表
  2. 每次访问数据时，将数据移到链表头部
  3. 淘汰时，删除链表尾部的数据

LFU的工作原理：

  1. 维护一个访问计数
  2. 每次访问数据时，增加计数
  3. 淘汰时，删除计数最小的数据

FIFO的工作原理：

  1. 维护一个插入队列
  2. 每次插入数据时，加入队列尾部
  3. 淘汰时，删除队列头部的数据

Redis的淘汰策略

  1. noeviction：不淘汰，内存满时返回错误
  2. allkeys-lru：在所有key中使用LRU
  3. volatile-lru：在设置了过期时间的key中使用LRU
  4. allkeys-random：在所有key中随机淘汰
  5. volatile-random：在设置了过期时间的key中随机淘汰
  6. volatile-ttl：淘汰TTL最小的key

noeviction：

  • 当内存满时，写操作返回错误
  • 读操作正常
  • 适用于不能丢失数据的场景

allkeys-lru：

  • 在所有key中使用LRU算法淘汰
  • 适用于缓存场景
  • 可能淘汰热点数据

volatile-lru：

  • 在设置了过期时间的key中使用LRU算法淘汰
  • 适用于混合场景（缓存+持久化）
  • 不会淘汰没有设置过期时间的key

缓存的高可用

主从复制

  • 主节点负责写操作
  • 从节点负责读操作
  • 数据异步复制

主从复制的工作原理：

  1. 客户端写入主节点
  2. 主节点将写操作同步到从节点
  3. 从节点执行写操作
  4. 客户端从从节点读取数据

主从复制的优点：

  • 读写分离，提升性能
  • 数据备份，提高可靠性
  • 故障转移，提高可用性

主从复制的缺点：

  • 数据延迟（异步复制）
  • 主节点单点
  • 需要处理故障转移

哨兵模式

  • 监控主从节点的健康状态
  • 主节点宕机时自动故障转移
  • 通知客户端新的主节点地址

哨兵模式的工作原理：

  1. 哨兵定期检查主从节点
  2. 如果主节点宕机，哨兵发起故障转移
  3. 哨兵选举新的主节点
  4. 哨兵通知客户端新的主节点地址

哨兵模式的优点：

  • 自动故障转移
  • 高可用
  • 客户端无需关心主节点地址

哨兵模式的缺点：

  • 需要额外部署哨兵
  • 故障转移期间可能有短暂不可用
  • 需要处理脑裂问题

集群模式

  • 数据自动分片
  • 节点之间互相通信
  • 支持动态扩缩容

集群模式的工作原理：

  1. 数据通过哈希槽分布到多个节点
  2. 每个节点负责一部分哈希槽
  3. 节点之间通过Gossip协议通信
  4. 客户端可以连接任意节点

集群模式的优点：

  • 自动分片
  • 高可用
  • 支持动态扩缩容

集群模式的缺点：

  • 实现复杂
  • 某些操作受限（如跨槽操作）
  • 需要客户端支持

缓存的监控

关键指标

  1. 命中率：缓存命中次数 / 总请求次数
  2. 内存使用率：已用内存 / 总内存
  3. 连接数：当前连接数
  4. QPS：每秒请求数
  5. 延迟：请求响应时间

命中率的意义：

命中率反映了缓存的有效性。命中率越高，说明缓存越有效，数据库压力越小

内存使用率的意义：

内存使用率反映了缓存的容量。如果内存使用率过高，可能会触发淘汰策略

QPS的意义：

QPS反映了缓存的负载。如果QPS过高，可能需要增加节点

监控工具

  1. Redis INFO：Redis自带的监控命令
  2. Redis Monitor：实时监控Redis命令
  3. Prometheus + Grafana：监控和可视化
  4. Redis Insight：Redis官方的监控工具

Redis INFO：

  • 查看Redis的运行状态
  • 包括内存、连接、命中率等信息
  • 命令：redis-cli info

Prometheus + Grafana：

  • Prometheus收集Redis指标
  • Grafana可视化展示
  • 支持告警

缓存的最佳实践

1. 合理设置过期时间

  • 热点数据可以设置较长的过期时间
  • 冷数据可以设置较短的过期时间
  • 避免大量数据同时过期

如何设置合理的过期时间？

  • 根据数据更新频率
  • 根据数据访问频率
  • 根据业务需求

2. 使用合适的数据结构

  • String：简单的key-value
  • Hash：对象存储
  • List：列表数据
  • Set：去重数据
  • ZSet：有序数据

String的适用场景：

  • 缓存单个值
  • 计数器
  • 分布式锁

Hash的适用场景：

  • 缓存对象
  • 用户信息
  • 商品信息

List的适用场景：

  • 消息队列
  • 最新列表
  • 排行榜

Set的适用场景：

  • 去重
  • 交集、并集、差集
  • 共同好友

ZSet的适用场景：

  • 排行榜
  • 延迟队列
  • 带权重的集合

3. 避免大key

  • 大key会阻塞Redis
  • 拆分大key为多个小key
  • 使用压缩算法

什么是大key？

  • String类型的value大于10KB
  • Hash、List、Set、ZSet类型的元素大于5000个

大key的问题：

  • 读写耗时长
  • 阻塞其他请求
  • 网络带宽占用大

如何处理大key？

  • 拆分大key
  • 使用压缩
  • 异步处理

4. 使用Pipeline

  • 批量操作使用Pipeline
  • 减少网络往返
  • 提升性能

Pipeline的工作原理：

  1. 客户端将多个命令打包
  2. 一次性发送给Redis
  3. Redis依次执行命令
  4. 一次性返回结果

Pipeline的优点：

  • 减少网络往返
  • 提升吞吐量
  • 降低延迟

5. 使用连接池

  • 使用连接池管理连接
  • 避免频繁创建和销毁连接
  • 设置合理的连接数

连接池的工作原理：

  1. 预先创建一定数量的连接
  2. 业务需要时从连接池获取连接
  3. 业务完成后归还连接到连接池
  4. 连接池负责连接的生命周期管理

连接池的优点：

  • 减少连接创建开销
  • 提升性能
  • 控制连接数

6. 序列化优化

  • 选择高效的序列化方式
  • 避免使用Java序列化
  • 推荐使用Protobuf、Kryo

序列化的方式：

  • JSON：可读性好，性能一般
  • Protobuf：性能好，可读性差
  • Kryo：性能好，可读性差
  • Java序列化：性能差，不推荐

多级缓存架构

本地缓存

  • 进程内缓存
  • 性能最高
  • 容量有限
  • 代表：Caffeine、Guava Cache

本地缓存的优点：

  • 无网络开销
  • 性能最高
  • 实现简单

本地缓存的缺点：

  • 容量有限
  • 数据不一致
  • 无法共享

分布式缓存

  • 跨进程共享
  • 容量大
  • 性能相对较低
  • 代表：Redis、Memcached

分布式缓存的优点：

  • 容量大
  • 可共享
  • 高可用

分布式缓存的缺点：

  • 网络开销
  • 性能相对较低
  • 实现复杂

多级缓存的读写流程

读流程

  1. 先读本地缓存
  2. 本地缓存没有，读分布式缓存
  3. 分布式缓存没有，读数据库
  4. 将结果写入缓存

写流程

  1. 更新数据库
  2. 删除分布式缓存
  3. 删除本地缓存（或等待过期）

总结

今天我们学习了分布式缓存的相关知识

  1. 分布式缓存的架构：客户端路由、代理层、集群模式
  2. 缓存的常见问题：穿透、击穿、雪崩、一致性
  3. 缓存的淘汰策略：LRU、LFU、FIFO、TTL
  4. 缓存的高可用：主从复制、哨兵模式、集群模式
  5. 缓存的最佳实践：合理设置过期时间、避免大key、使用Pipeline
  6. 多级缓存架构：本地缓存 + 分布式缓存

分布式缓存是提升系统性能的重要手段，合理使用缓存可以大大提升系统的吞吐量和响应速度
