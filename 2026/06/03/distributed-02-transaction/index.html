分布式事务：从理论到实践

2026-06-03 分布式 2PC, Saga, TCC, 事务, 分布式 0 Comments Word Count: 3.8k(words) Read Count: 13(minutes)

前言

在单体应用中，我们可以使用数据库事务来保证数据一致性。但是在分布式系统中，一个业务操作可能涉及多个服务、多个数据库，传统的事务机制就无法满足需求了。今天就来聊聊分布式事务的各种解决方案，以及它们各自的优缺点和适用场景

什么是分布式事务

分布式事务是指事务的参与者、支持事务的服务器、资源服务器以及事务管理器分别位于分布式系统的不同节点之上

简单来说，分布式事务就是要保证多个服务之间的数据一致性

为什么需要分布式事务

假设一个电商系统，下单操作需要：

  1. 订单服务：创建订单
  2. 库存服务：扣减库存
  3. 账户服务：扣减余额

如果订单创建成功，但库存扣减失败，就会出现数据不一致

分布式事务的挑战

  1. 网络不可靠：网络可能延迟、丢包、分区
  2. 节点可能宕机：任何节点都可能在任何时候宕机
  3. 性能问题：分布式事务通常需要多次网络通信
  4. 数据一致性：如何保证所有节点的数据最终一致

分布式事务的分类

刚性事务

刚性事务要求强一致性，通常基于XA协议实现

  • 代表：2PC（两阶段提交）
  • 特点：强一致性、性能差、可用性低

柔性事务

柔性事务允许最终一致性，通常基于BASE理论实现

  • 代表：TCC、Saga、本地消息表
  • 特点：最终一致性、性能好、可用性高

两阶段提交（2PC）

什么是2PC

两阶段提交（Two-Phase Commit）是最经典的分布式事务协议

2PC的两个阶段

阶段一：准备阶段（Prepare Phase）

  1. 协调者向所有参与者发送Prepare请求
  2. 参与者执行本地事务，但不提交
  3. 参与者返回Yes或No

阶段二：提交阶段（Commit Phase）

  1. 如果所有参与者都返回Yes，协调者发送Commit请求
  2. 如果有参与者返回No，协调者发送Rollback请求
  3. 参与者执行提交或回滚

2PC的问题

同步阻塞

所有参与者在准备阶段后必须等待协调者的最终决定，这期间资源被锁定

为什么会阻塞？

参与者在准备阶段已经执行了本地事务（但不提交），锁定了数据库资源。在等待协调者决定期间，这些资源一直被锁定，其他事务无法访问

阻塞的影响：

  • 数据库连接被占用
  • 行锁或表锁被持有
  • 并发性能下降

单点故障

协调者是单点，如果协调者宕机，参与者将一直处于锁定状态

为什么是单点？

2PC协议中只有一个协调者，所有参与者都依赖协调者来做出最终决定

单点故障的影响：

  • 协调者宕机后，参与者无法知道应该提交还是回滚
  • 参与者的资源一直被锁定
  • 系统可能需要人工干预来恢复

数据不一致

如果在阶段二，协调者发送Commit后宕机，部分参与者收到Commit，部分没有收到，会导致数据不一致

为什么会不一致？

假设协调者向参与者A发送了Commit，但向参与者B发送Commit之前宕机了：

  • 参与者A收到Commit，提交了事务
  • 参与者B没有收到Commit，不知道应该提交还是回滚
  • 结果：A和B的数据不一致

2PC的适用场景

  • 对一致性要求极高的场景
  • 性能要求不高的场景
  • 传统数据库的分布式事务

三阶段提交（3PC）

什么是3PC

三阶段提交是对2PC的改进，增加了一个CanCommit阶段

3PC的三个阶段

阶段一：CanCommit阶段

  1. 协调者向所有参与者发送CanCommit请求
  2. 参与者判断是否可以执行事务
  3. 参与者返回Yes或No

CanCommit阶段的作用：

  • 检查参与者是否可以执行事务
  • 避免不必要的资源锁定
  • 减少阻塞时间

阶段二：PreCommit阶段

  1. 如果所有参与者都返回Yes，协调者发送PreCommit请求
  2. 参与者执行本地事务，但不提交
  3. 参与者返回Ack

阶段三：DoCommit阶段

  1. 协调者发送DoCommit请求
  2. 参与者提交事务

3PC如何解决2PC的问题

减少阻塞

3PC在CanCommit阶段就检查参与者是否可以执行，避免了不必要的资源锁定

超时机制

3PC引入了超时机制：如果参与者在规定时间内没有收到协调者的决定，它会默认提交事务

为什么可以默认提交？

在3PC中，如果参与者收到了PreCommit，说明所有参与者都同意了，所以可以安全地提交

3PC的问题

  1. 网络分区时仍可能出现数据不一致：超时机制不能完全解决问题
  2. 实现复杂度增加：多了一个阶段，实现更复杂

TCC（Try-Confirm-Cancel）

什么是TCC

TCC是一种补偿型事务，将业务分为三个阶段

TCC的三个阶段

Try阶段

  • 预留资源
  • 检查业务条件
  • 但不执行真正的业务操作

Try阶段做什么？

以转账为例：

  • 检查A账户余额是否充足
  • 冻结A账户的转账金额
  • 检查B账户是否正常

为什么要冻结而不是直接扣减？

因为Try阶段可能会失败，如果直接扣减，失败后需要回滚，回滚可能失败（比如网络问题）。冻结可以避免这个问题，Cancel时只需要解冻

Confirm阶段

  • 执行真正的业务操作
  • 使用Try阶段预留的资源
  • Confirm操作必须保证幂等

Confirm阶段做什么？

以转账为例：

  • A账户扣除冻结金额
  • B账户增加金额

为什么Confirm必须幂等？

因为Confirm可能会被重试，如果Confirm不是幂等的，可能会导致重复扣款或重复加款

Cancel阶段

  • 释放Try阶段预留的资源
  • Cancel操作必须保证幂等

Cancel阶段做什么？

以转账为例：

  • 解冻A账户的冻结金额

为什么Cancel必须幂等？

因为Cancel可能会被重试，如果Cancel不是幂等的，可能会导致重复解冻

TCC的问题

  1. 业务侵入性强：每个业务都需要实现Try、Confirm、Cancel三个接口
  2. 空回滚：Try没有执行，但Cancel被调用
  3. 悬挂：Cancel先于Try执行
  4. 幂等性：Confirm和Cancel必须保证幂等

空回滚问题

什么是空回滚？

当Try没有执行（比如超时），但Cancel被调用了，这就是空回滚

为什么会发生？

  • Try请求超时
  • 协调者认为Try失败，发送Cancel
  • 实际上Try可能还在执行

如何处理？

Cancel需要检查Try是否执行过，如果没有执行过，直接返回成功

悬挂问题

什么是悬挂？

Cancel先于Try执行，导致Try执行后资源被冻结，但无法Confirm或Cancel

为什么会发生？

  • Cancel先到达并执行
  • Try后到达并执行
  • 资源被冻结，但无法释放

如何处理？

Try需要检查Cancel是否执行过，如果执行过，直接返回失败

TCC的适用场景

  • 对一致性要求较高的场景
  • 业务可以拆分为Try、Confirm、Cancel
  • 性能要求较高的场景

Saga

什么是Saga

Saga是一种长事务解决方案，将长事务拆分为多个本地事务

Saga的两种实现

协同式（Choreography）

  • 每个服务监听事件并执行本地事务
  • 服务之间通过事件通信
  • 没有中心化的协调者

协同式的工作流程：

协同式的优点：

  • 松耦合：服务之间只通过事件通信
  • 简单：不需要中心化协调者
  • 可扩展：容易添加新服务

协同式的缺点：

  • 难以理解：事件流分散在各个服务中
  • 难以调试：问题定位困难
  • 循环依赖：服务之间可能有循环依赖

编排式（Orchestration）

  • 有一个中心化的协调者
  • 协调者负责调用各个服务
  • 协调者处理失败和补偿

编排式的工作流程：

编排式的优点：

  • 易于理解：流程集中在一个地方
  • 易于调试：问题定位容易
  • 易于控制：协调者控制整个流程

编排式的缺点：

  • 耦合性强：协调者依赖所有服务
  • 单点故障：协调者是单点
  • 复杂度高：协调者逻辑复杂

Saga的补偿机制

每个本地事务都有一个对应的补偿事务

补偿事务的作用：

  • 撤销已经执行的操作
  • 保证数据最终一致
  • 处理失败情况

补偿事务的特点：

  • 必须幂等：可能会被重试
  • 必须可串行化：补偿顺序很重要
  • 必须可交换：补偿可以和正向操作交换

Saga的问题

  1. 没有隔离性：中间状态对外可见
  2. 补偿复杂：补偿逻辑可能很复杂
  3. 最终一致性：只能保证最终一致性

隔离性问题

为什么没有隔离性？

Saga中，每个本地事务都会立即提交，中间状态对外可见

举例：

在T1和T2之间，订单状态是”待支付”，但库存还没有扣减，其他用户可能看到这个订单

如何解决？

  • 语义锁：在业务层面加锁
  • 读取未提交数据：允许读取中间状态
  • 重新排序：调整事务顺序

Saga的适用场景

  • 长流程业务
  • 跨多个服务的业务
  • 对隔离性要求不高的场景

本地消息表

什么是本地消息表

本地消息表是一种基于消息队列的分布式事务方案

实现步骤

  1. 业务操作和消息插入在同一个本地事务中
  2. 定时任务扫描未发送的消息
  3. 将消息发送到消息队列
  4. 消费者处理消息并确认
  5. 更新消息状态

详细流程：

本地消息表的优点

  1. 实现简单
  2. 保证最终一致性
  3. 性能较好

本地消息表的问题

  1. 需要额外的消息表
  2. 定时任务的延迟
  3. 消费者需要保证幂等

定时任务延迟

为什么会延迟？

定时任务每隔一段时间扫描一次，扫描间隔就是延迟

如何减少延迟？

  • 减少扫描间隔
  • 使用消息队列的延迟消息
  • 使用数据库的触发器

幂等性问题

为什么需要幂等？

消息可能会重复发送，消费者需要保证重复处理不会产生副作用

如何保证幂等？

  • 使用唯一标识
  • 使用状态机
  • 使用数据库唯一约束

事务消息

什么是事务消息

事务消息是消息队列提供的分布式事务解决方案

事务消息的流程

  1. 发送半消息（Half Message）
  2. 执行本地事务
  3. 根据本地事务结果提交或回滚半消息
  4. 如果没有收到确认，消息队列会回查

详细流程：

事务消息的例子

以RocketMQ为例：

  1. 发送Half Message
  2. 执行本地事务
  3. 根据结果Commit或Rollback
  4. 如果超时未确认，RocketMQ会回查

回查机制：

  • RocketMQ定期检查未确认的半消息
  • 调用生产者的回查接口
  • 根据回查结果决定提交或回滚

事务消息的优点

  1. 性能好
  2. 实现相对简单
  3. 消息队列保证可靠性

事务消息的问题

  1. 依赖消息队列
  2. 回查机制的实现
  3. 消费者需要保证幂等

分布式事务的选型

选型维度

方案 一致性 性能 复杂度 适用场景
2PC 强一致 低 低 传统数据库
3PC 强一致 中 中 改进版2PC
TCC 最终一致 高 高 高性能场景
Saga 最终一致 高 中 长流程业务
本地消息表 最终一致 高 低 异步场景
事务消息 最终一致 高 低 消息驱动

选型建议

  1. 强一致性要求：2PC、3PC
  2. 高性能要求：TCC、Saga
  3. 实现简单：本地消息表、事务消息
  4. 长流程业务：Saga
  5. 消息驱动：事务消息

分布式事务的最佳实践

1. 尽量避免分布式事务

  • 业务设计时尽量避免跨服务事务
  • 使用聚合根模式
  • 考虑最终一致性

2. 选择合适的方案

  • 根据业务场景选择合适的方案
  • 不要过度设计
  • 考虑团队的技术栈

3. 保证幂等性

  • 所有分布式事务方案都需要保证幂等性
  • 使用唯一标识
  • 使用状态机

4. 处理异常情况

  • 网络超时
  • 服务宕机
  • 数据不一致

5. 监控和告警

  • 监控事务状态
  • 告警异常情况
  • 记录事务日志

总结

今天我们学习了分布式事务的各种解决方案

  1. 2PC：经典方案，强一致性，但性能差
  2. 3PC：2PC的改进，减少锁定时间
  3. TCC：补偿型事务，高性能，但业务侵入性强
  4. Saga：长事务解决方案，适合长流程业务
  5. 本地消息表：基于消息队列，实现简单
  6. 事务消息：消息队列提供的方案，性能好

选择合适的分布式事务方案需要根据业务场景、性能要求、一致性要求等因素综合考虑
