分布式系统理论基础：从CAP到一致性协议

2026-06-03 分布式 CAP, 一致性, 分布式, 理论 0 Comments Word Count: 2k(words) Read Count: 7(minutes)

前言

在后端开发中，分布式系统已经成为了标配。但是你有没有想过，为什么分布式系统这么难设计？为什么总是要在一致性、可用性、分区容错性之间做选择？今天就来聊聊分布式系统的理论基础，这些理论是理解所有分布式系统的基石

CAP定理

什么是CAP

CAP定理是分布式系统中最著名的理论之一，由Eric Brewer在2000年提出

CAP代表三个特性：

  • C（Consistency）一致性：所有节点在同一时间看到相同的数据
  • A（Availability）可用性：每个请求都能收到一个（非错误）响应
  • P（Partition Tolerance）分区容错性：系统在网络分区的情况下仍能继续运行

CAP的不可能三角

CAP定理指出，在一个分布式系统中，最多只能同时满足这三个特性中的两个

这意味着我们只能在以下三种组合中选择：

  1. CP系统：保证一致性和分区容错性，但可能牺牲可用性
  2. AP系统：保证可用性和分区容错性，但可能牺牲一致性
  3. CA系统：保证一致性和可用性，但无法处理分区

为什么P是必须的

在分布式系统中，网络分区是不可避免的。网络可能断开、服务器可能宕机、延迟可能很高。因此，实际上我们只能在CP和AP之间选择

CP系统的例子

  • ZooKeeper：分布式协调服务，保证强一致性
  • etcd：键值存储，用于配置管理
  • HBase：分布式数据库，保证强一致性

当发生网络分区时，CP系统可能会拒绝某些请求，以保证一致性

AP系统的例子

  • Cassandra：分布式数据库，保证最终一致性
  • DynamoDB：亚马逊的键值存储
  • Eureka：服务注册中心

当发生网络分区时，AP系统可能会返回过期数据，但保证服务可用

BASE理论

什么是BASE

BASE理论是对CAP定理的延伸，它提出了另一种思路

BASE代表：

  • BA（Basically Available）基本可用：系统保证基本可用，允许损失部分可用性
  • S（Soft State）软状态：系统状态可以随时间变化，不要求实时一致
  • E（Eventually Consistent）最终一致性：系统最终会达到一致状态

BASE vs ACID

特性 ACID BASE
一致性 强一致性 最终一致性
可用性 可能牺牲 基本可用
事务 严格事务 柔性事务
适用场景 传统数据库 分布式系统

最终一致性的模型

最终一致性有多种变体：

  1. 因果一致性：保证因果关系的操作顺序
  2. 读己之所写：用户总能读到自己写的数据
  3. 会话一致性：在会话范围内保证一致性
  4. 单调读一致性：读取操作不会读到更旧的数据
  5. 单调写一致性：写操作按顺序执行

一致性协议

Paxos

什么是Paxos

Paxos是Lamport在1990年提出的一致性协议，被公认为最难理解的分布式协议之一

Paxos解决的问题是：在一个可能发生网络分区的分布式系统中，如何就某个值达成一致

Paxos的角色

Paxos中有三种角色：

  1. Proposer（提议者）：提出提案
  2. Acceptor（接受者）：投票决定是否接受提案
  3. Learner（学习者）：学习最终达成一致的值

Paxos的两个阶段

阶段一：Prepare阶段

  1. Proposer选择一个提案号n，向所有Acceptor发送Prepare(n)请求
  2. Acceptor收到Prepare(n)后，如果n大于它已经响应的所有提案号，则承诺不再接受编号小于n的提案
  3. Acceptor返回它已经接受的最大编号提案

阶段二：Accept阶段

  1. 如果Proposer收到了多数Acceptor的响应，它会发送Accept(n, v)请求
  2. v是响应中编号最大的提案的值，如果没有则Proposer可以自己决定值
  3. Acceptor收到Accept(n, v)后，如果n不小于它承诺的最小提案号，则接受该提案

Paxos的问题

  1. 活锁问题：多个Proposer交替提出提案，导致无法达成一致
  2. 实现复杂：Paxos的正确实现非常困难
  3. 性能问题：需要两轮通信

Raft

什么是Raft

Raft是2014年提出的一致性协议，设计目标是比Paxos更容易理解

Raft将问题分解为三个子问题：

  1. 领导选举（Leader Election）
  2. 日志复制（Log Replication）
  3. 安全性（Safety）

Raft的角色

Raft中有三种角色：

  1. Leader（领导者）：处理所有客户端请求
  2. Follower（追随者）：被动接收Leader的指令
  3. Candidate（候选者）：参与领导选举

领导选举

  1. 所有节点初始状态为Follower
  2. Follower在超时后变为Candidate，发起选举
  3. Candidate向其他节点请求投票
  4. 获得多数票的Candidate变为Leader
  5. Leader定期发送心跳维持领导地位

日志复制

  1. 客户端发送命令给Leader
  2. Leader将命令追加到日志
  3. Leader并行发送AppendEntries RPC给所有Follower
  4. 多数Follower确认后，Leader提交日志
  5. Leader通知Follower提交日志

安全性

  • 选举限制：只有包含所有已提交日志的节点才能成为Leader
  • 提交规则：Leader只能提交当前任期的日志
  • 日志匹配：如果两个日志在某个索引处相同，则之前的所有日志也相同

ZAB协议

什么是ZAB

ZAB（ZooKeeper Atomic Broadcast）是ZooKeeper使用的协议

ZAB有两种模式：

  1. 崩溃恢复（Recovery）：选举新的Leader
  2. 消息广播（Broadcast）：Leader广播消息给Follower

ZAB vs Raft

特性 ZAB Raft
选举 基于zxid 基于任期
日志复制 两阶段 追加
提交 两阶段 多数确认

一致性哈希

为什么需要一致性哈希

在分布式系统中，我们经常需要将数据分布到多个节点。传统的取模哈希（hash % n）有一个问题：当节点数量变化时，几乎所有数据都需要重新分布

一致性哈希的原理

一致性哈希将整个哈希值空间组织成一个虚拟的环：

  1. 将节点映射到环上
  2. 将数据映射到环上
  3. 数据由顺时针方向遇到的第一个节点负责

数据倾斜问题

当节点数量较少时，可能会出现数据分布不均匀的问题

解决方案：虚拟节点

每个物理节点对应多个虚拟节点，虚拟节点均匀分布在环上

分布式ID生成

为什么需要分布式ID

在分布式系统中，我们需要生成全局唯一的ID，用于标识订单、用户、消息等

常见方案

UUID

  • 优点：简单、无中心化
  • 缺点：无序、存储空间大、不适合做主键

数据库自增

  • 优点：简单、有序
  • 缺点：单点瓶颈、扩展性差

号段模式

  • 使用数据库存储号段，应用从号段中获取ID
  • 优点：性能好、扩展性好
  • 缺点：实现复杂

Snowflake算法

  • 64位ID = 1位符号 + 41位时间戳 + 10位机器ID + 12位序列号
  • 优点：有序、高性能、去中心化
  • 缺点：依赖时钟

总结

今天我们学习了分布式系统的理论基础

  1. CAP定理：一致性、可用性、分区容错性三选二
  2. BASE理论：基本可用、软状态、最终一致性
  3. 一致性协议：Paxos、Raft、ZAB
  4. 一致性哈希：解决数据分布问题
  5. 分布式ID：解决全局唯一ID问题
