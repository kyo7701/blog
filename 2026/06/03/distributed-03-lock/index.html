分布式锁：原理、实现与选型

2026-06-03 分布式 Redis, ZooKeeper, 分布式, 锁 0 Comments Word Count: 4.3k(words) Read Count: 15(minutes)

前言

在单体应用中，我们可以使用JVM内置的锁机制（synchronized、ReentrantLock）来保证线程安全。但是在分布式系统中，多个应用实例运行在不同的JVM中，甚至不同的机器上，JVM内置的锁就无法满足需求了。今天就来聊聊分布式锁的各种实现方案，以及它们各自的优缺点和适用场景

什么是分布式锁

分布式锁是在分布式系统中，用于控制多个进程对共享资源访问的一种机制

简单来说，分布式锁就是要保证在分布式环境下，同一时刻只有一个进程能够访问共享资源

为什么需要分布式锁

假设一个电商系统，多个服务实例同时处理订单：

结果：库存应该是8，但实际是9，出现了超卖问题

分布式锁的应用场景

  1. 秒杀系统：防止超卖
  2. 任务调度：防止任务重复执行
  3. 配置更新：防止并发更新
  4. 限流控制：控制并发数

分布式锁的特性

一个完善的分布式锁需要满足以下特性

1. 互斥性

同一时刻只能有一个客户端持有锁

什么是互斥？

互斥是指在同一时刻，只有一个客户端能够获取到锁。其他客户端必须等待，直到锁被释放

如何保证互斥？

  • 使用原子操作（如SETNX）
  • 使用唯一标识（如UUID）
  • 使用过期时间

2. 避免死锁

锁必须有超时机制，防止持有锁的客户端宕机导致死锁

什么是死锁？

死锁是指客户端获取锁后宕机，锁无法释放，其他客户端永远无法获取锁

如何避免死锁？

  • 设置过期时间
  • 使用看门狗机制
  • 使用临时节点（ZooKeeper）

3. 可重入性

同一个客户端可以多次获取同一把锁

什么是可重入？

可重入是指同一个客户端（或线程）可以多次获取同一把锁，而不会被自己阻塞

为什么需要可重入？

如果锁不可重入，methodA调用methodB时会死锁

如何实现可重入？

  • 使用计数器记录重入次数
  • 使用线程ID标识持有者
  • 释放时检查计数器

4. 高可用

锁服务需要高可用，避免单点故障

什么是高可用？

高可用是指锁服务在部分节点故障时仍能正常工作

如何保证高可用？

  • 主从复制
  • 集群部署
  • 一致性协议（如Raft）

5. 高性能

获取和释放锁的性能要高

为什么需要高性能？

分布式锁是热点资源，每次业务操作都需要获取和释放锁，如果锁的性能差，会成为系统瓶颈

如何提高性能？

  • 减少网络通信
  • 使用缓存
  • 批量操作

基于数据库的分布式锁

实现方式

基于唯一索引

创建一张锁表，使用唯一索引来实现互斥

获取锁时，插入一条记录，如果插入成功则表示获取锁成功

工作原理：

  1. 尝试插入一条记录
  2. 如果插入成功（唯一索引不冲突），获取锁成功
  3. 如果插入失败（唯一索引冲突），获取锁失败
  4. 释放锁时，删除记录

为什么使用唯一索引？

唯一索引保证了同一个lock_key只能有一条记录，从而保证了互斥性

基于悲观锁

使用SELECT FOR UPDATE来实现

工作原理：

  1. 执行SELECT FOR UPDATE
  2. 数据库对查询到的行加锁
  3. 其他事务无法修改这些行
  4. 当前事务提交或回滚后释放锁

为什么使用悲观锁？

悲观锁假设会发生冲突，所以在读取数据时就加锁，防止其他事务修改

基于乐观锁

使用版本号来实现

工作原理：

  1. 读取当前版本号
  2. 更新时检查版本号是否变化
  3. 如果版本号没变，更新成功
  4. 如果版本号变了，更新失败，重试

为什么使用乐观锁？

乐观锁假设不会发生冲突，只在更新时检查，性能更好

数据库锁的优缺点

优点

  • 实现简单
  • 易于理解
  • 不需要额外组件

缺点

  • 性能差（数据库IO）
  • 可用性低（数据库单点）
  • 死锁风险（连接池耗尽）
  • 不支持可重入

为什么性能差？

每次获取和释放锁都需要访问数据库，数据库IO是性能瓶颈

为什么可用性低？

数据库是单点，如果数据库宕机，锁服务不可用

为什么有死锁风险？

如果获取锁后没有释放，数据库连接被占用，可能导致连接池耗尽

适用场景

  • 并发量低的场景
  • 对性能要求不高的场景
  • 已有数据库，不想引入额外组件

基于Redis的分布式锁

基本实现

使用SETNX命令实现

  • NX：只有key不存在时才设置
  • PX：设置过期时间（毫秒）

工作原理：

  1. 执行SET命令，设置NX和PX
  2. 如果key不存在，设置成功，获取锁成功
  3. 如果key存在，设置失败，获取锁失败
  4. 过期时间到，key自动删除，锁自动释放

为什么使用SETNX？

SETNX是原子操作，保证了”检查并设置”的原子性

为什么使用PX？

PX设置了过期时间，避免了死锁问题

释放锁

使用Lua脚本保证原子性

为什么要使用Lua脚本？

释放锁需要先检查锁的值是否是自己设置的，然后再删除。这两个操作必须是原子的，否则可能会删除别人的锁

Lua脚本的工作原理：

  1. 获取锁的值
  2. 检查是否等于自己设置的值
  3. 如果相等，删除锁
  4. 如果不相等，返回失败

Redis锁的问题

1. 锁超时问题

如果业务执行时间超过锁的超时时间，锁会自动释放，可能导致并发问题

为什么会超时？

  • 业务执行时间过长
  • 网络延迟
  • GC暂停

超时的影响：

  • 锁被释放
  • 其他客户端获取到锁
  • 两个客户端同时操作共享资源

解决方案：

  • 使用看门狗机制，自动续期
  • 评估业务执行时间，设置合理的超时时间

看门狗机制的工作原理：

  1. 获取锁时启动看门狗
  2. 看门狗定期检查锁是否还被持有
  3. 如果还被持有，延长过期时间
  4. 业务完成后，停止看门狗，释放锁

2. 主从切换问题

Redis主从架构下，主节点宕机，从节点提升为主节点，可能导致锁丢失

为什么会丢锁？

解决方案：

  • 使用RedLock算法
  • 使用单节点Redis（牺牲可用性）

3. 不可重入问题

默认实现不支持可重入

为什么不可重入？

SETNX只能设置一次，如果再次设置会失败

解决方案：

  • 使用Hash结构记录重入次数
  • 使用Redisson等客户端

RedLock算法

什么是RedLock

RedLock是Redis作者提出的分布式锁算法，基于多个独立的Redis实例

RedLock的步骤

  1. 获取当前时间
  2. 依次向N个Redis实例请求加锁
  3. 计算获取锁花费的时间
  4. 如果在多数实例（N/2+1）上加锁成功，且花费时间小于锁的有效时间，则认为加锁成功
  5. 如果加锁失败，向所有实例发送释放锁请求

为什么RedLock能解决主从切换问题

RedLock使用多个独立的Redis实例，即使某个实例宕机，其他实例仍然可用

RedLock的安全性：

  • 需要多数派成功：即使少数实例故障，仍然可以工作
  • 需要时间检查：确保锁的有效期足够长
  • 需要独立实例：避免单点故障

RedLock的问题

  1. 依赖时钟同步：如果Redis实例的时钟不同步，可能会有问题
  2. 性能开销大：需要访问多个Redis实例
  3. 实现复杂：比单节点Redis复杂

Redisson

什么是Redisson

Redisson是一个Java的Redis客户端，提供了完善的分布式锁实现

Redisson的特性

  1. 可重入锁：支持同一个线程多次加锁
  2. 看门狗机制：自动续期
  3. 公平锁：按照请求顺序获取锁
  4. 读写锁：支持读写分离
  5. 联锁：同时获取多个锁
  6. 红锁：基于RedLock算法

看门狗机制：

Redisson内置了看门狗机制，会自动延长锁的过期时间，默认30秒续期一次

公平锁：

公平锁保证等待时间最长的客户端最先获取锁，避免饥饿问题

读写锁：

读写锁允许多个读操作并发执行，但写操作是互斥的

Redis锁的优缺点

优点

  • 性能高
  • 实现简单
  • 支持可重入

缺点

  • 主从切换可能丢锁
  • 依赖时钟同步
  • 需要处理续期问题

适用场景

  • 高并发场景
  • 对性能要求高的场景
  • 可以接受极端情况下锁失效

基于ZooKeeper的分布式锁

实现原理

基于ZooKeeper的临时顺序节点实现

获取锁

  1. 在指定节点下创建临时顺序节点
  2. 获取该节点下的所有子节点
  3. 判断自己是否是最小的节点
  4. 如果是，则获取锁成功
  5. 如果不是，则监听比自己小的节点
  6. 当监听的节点删除时，重新判断

详细流程：

释放锁

  1. 删除自己创建的临时节点
  2. 会话结束时自动删除

为什么使用临时节点？

临时节点在会话结束时自动删除，避免了死锁问题

为什么使用顺序节点？

顺序节点保证了公平性，等待时间最长的客户端最先获取锁

ZooKeeper锁的特性

1. 可重入性

通过记录节点路径实现可重入

如何实现可重入？

  • 记录当前客户端创建的节点路径
  • 再次获取锁时，检查是否已经创建过节点
  • 如果已经创建过，增加重入计数

2. 避免死锁

临时节点在会话结束时自动删除

为什么能避免死锁？

如果客户端宕机，会话结束，临时节点自动删除，锁自动释放

3. 公平性

顺序节点保证公平性

为什么是公平的？

顺序节点按照创建顺序编号，最小的节点最先获取锁，保证了先到先得

4. 高可用

ZooKeeper集群保证高可用

如何保证高可用？

  • ZooKeeper集群通常有3个或5个节点
  • 只要多数节点存活，集群就能正常工作
  • 使用ZAB协议保证数据一致性

Curator

什么是Curator

Curator是Apache的ZooKeeper客户端，提供了分布式锁的实现

Curator提供的锁

  1. InterProcessMutex：可重入锁
  2. InterProcessSemaphoreMutex：不可重入锁
  3. InterReadWriteLock：读写锁
  4. InterProcessMultiLock：联锁
  5. InterProcessSemaphore：信号量

InterProcessMutex的实现：

  • 使用临时顺序节点
  • 支持可重入
  • 支持公平锁
  • 自动处理会话超时

ZooKeeper锁的优缺点

优点

  • 强一致性
  • 避免死锁
  • 公平性
  • 高可用

缺点

  • 性能相对较低
  • 依赖ZooKeeper集群
  • 实现复杂

为什么性能相对较低？

每次获取和释放锁都需要创建和删除节点，涉及网络通信和磁盘IO

为什么依赖ZooKeeper集群？

ZooKeeper锁依赖ZooKeeper集群，需要额外部署和维护

适用场景

  • 对一致性要求高的场景
  • 已有ZooKeeper集群
  • 可以接受性能稍低

基于Etcd的分布式锁

实现原理

基于Etcd的租约（Lease）和事务（Transaction）实现

获取锁

  1. 创建租约
  2. 使用事务尝试创建key
  3. 如果创建成功，则获取锁成功
  4. 如果创建失败，则监听key的变化

详细流程：

释放锁

  1. 撤销租约
  2. key自动删除

为什么使用租约？

租约有TTL，到期后自动删除，避免了死锁问题

为什么使用事务？

事务保证了”检查并创建”的原子性

Etcd锁的特性

  1. 强一致性：基于Raft协议
  2. 租约机制：自动过期
  3. 事务支持：保证原子性
  4. Watch机制：支持监听

为什么强一致性？

Etcd使用Raft协议，保证了数据的强一致性

为什么使用租约？

租约机制避免了死锁问题，客户端宕机后，租约到期，锁自动释放

Etcd锁的优缺点

优点

  • 强一致性
  • 高可用
  • 支持租约

缺点

  • 性能相对较低
  • 需要Etcd集群
  • Go生态更好

适用场景

  • Kubernetes环境
  • 对一致性要求高的场景
  • Go技术栈

分布式锁的选型

选型维度

方案 一致性 性能 可用性 复杂度 适用场景
数据库 强 低 低 低 低并发
Redis 弱 高 高 低 高并发
ZooKeeper 强 中 高 中 强一致
Etcd 强 中 高 中 K8s环境

选型建议

  1. 高并发场景：Redis
  2. 强一致性场景：ZooKeeper、Etcd
  3. 已有基础设施：选择已有的
  4. Kubernetes环境：Etcd
  5. 简单场景：数据库

分布式锁的最佳实践

1. 设置合理的超时时间

  • 超时时间要大于业务执行时间
  • 考虑网络延迟
  • 使用续期机制

如何设置合理的超时时间？

  • 评估业务执行时间
  • 考虑网络延迟
  • 预留一些缓冲时间
  • 使用看门狗机制自动续期

2. 保证锁的唯一性

  • 使用UUID作为锁的value
  • 释放锁时验证value

为什么要验证value？

防止释放别人的锁。比如：

  1. 客户端A获取锁
  2. 客户端A执行时间过长，锁超时释放
  3. 客户端B获取锁
  4. 客户端A执行完成，释放锁
  5. 如果不验证value，客户端A会释放客户端B的锁

3. 处理锁失效

  • 使用幂等性设计
  • 使用分布式ID
  • 记录操作日志

如何处理锁失效？

  • 业务层面保证幂等
  • 使用分布式ID唯一标识操作
  • 记录操作日志，便于排查问题

4. 监控锁的使用

  • 监控锁的获取和释放
  • 告警锁的超时
  • 记录锁的等待时间

监控哪些指标？

  • 锁的获取成功率
  • 锁的等待时间
  • 锁的持有时间
  • 锁的超时次数

5. 避免锁的滥用

  • 尽量减少锁的粒度
  • 使用乐观锁替代悲观锁
  • 考虑无锁设计

如何减少锁的粒度？

  • 按业务拆分锁
  • 使用分段锁
  • 使用读写锁

总结

今天我们学习了分布式锁的各种实现方案

  1. 数据库锁：实现简单，但性能差
  2. Redis锁：性能高，但一致性弱
  3. ZooKeeper锁：强一致性，但性能中等
  4. Etcd锁：强一致性，适合K8s环境

选择合适的分布式锁方案需要根据业务场景、性能要求、一致性要求等因素综合考虑
